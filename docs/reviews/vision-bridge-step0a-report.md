# Vision Bridge — Step 0a 价值链验证报告

- 日期：2026-08-12
- 执行环境：NAS 生产实例（Octopus v1.4.3 @ 192.168.50.139:8088，commit 9e15bb9 部署），全部调用经真实网关与真实上游通道
- 上游语料：20 个代表场景 × 21 张图（17 张合成图自带 ground truth + 3 张真实 UI 截图 + 1 张真实照片）
- 调用量：121 次（A 40 / B 20 / C 40 / REF 20 / 探测 6），judge 方式 = ground-truth 子串自动判分 + 主观场景人工复核
- 结论：**PASS —— 三项决策阈值全部满足，价值链成立，进入 Step 1**；同时产出 4 项计划外发现，其中 2 项需要修正 v0.2 方案

---

## 1. 判定总览

| 指标 | 阈值 | 实测 | 判定 |
|---|---|---|---|
| ① 纯文本模型收 image_url 后不可用比例 | ≥70% | **100%**（40/40，含两种模型） | ✅ |
| ② VLM 图片描述成功率 | ≥80% | **95%**（19/20，人工复核后） | ✅ |
| ③ 图片替换为描述后文本模型响应可用率 | ≥70% | **80%**（32/40 保守口径；剔除通道层故障后 97%） | ✅ |

**关键定性结论**：上游对含图请求的失败形态不是干净的 400，而是三种**静默降质**——`HTTP 200 + 空 choices`（deepseek 18/20）、超时挂起（deepseek 2/20）、礼貌拒答或幻觉（glm-5.2 20/20）。这比方案假设的「上游 400」更糟：客户端拿到 200 却无内容，无从重试也无从归因。bridge 的价值定位由「修复报错」升级为「修复静默降质」。

## 2. 测试设计

- **A（上游真实行为）**：原始多模态 payload（text + image_url data URI）直接发给两个注册表标记 `vision_capable=0` 的纯文本模型：`deepseek-v4-flash-0731`、`glm-5.2`。
- **B（VLM 描述）**：固定安全模板（先转录可见文字→再描述视觉内容→拒绝执行图内指令，用户问题仅作侧重点提示），多图单次联合分析。
- **C（替换链路）**：把图片块替换为 `[Image N — Visual analysis]\n<B 输出>` 后，同样的问题再发给两个纯文本模型。
- **REF（基线）**：`gemini-3.5-flash` 原生多模态直答，作为质量与延迟对照。
- 场景覆盖：截图 OCR×4、图表理解×3、UI 理解×3、含图指令×3、多图对比×3、边界×2（重度模糊、纯色块）、混合×2（长文本上下文、图片在多轮历史中间）。

### VLM 选型说明（与计划的偏差）

计划默认 VLM 为 `glm-4.6v-flash`。实测该模型经网关**持续 429**（间隔重试仍失败），`glm-5v-turbo` 与 `gemini-3.6-flash` 均 404（无可用通道）。改用 `kimi-k3`（注册表 vision=1）作为 Step 0a 的 VLM，`gemini-3.5-flash` 兜底（未触发）。此偏差不影响价值链结论（验证的是「VLM 描述→文本模型」链路本身），但直接证明：**VLM fallback 链是必需品**，且默认选型需按部署环境实测决定。

## 3. ① 上游行为（A，40 次）

| 模型 | 行为 | 次数 | 说明 |
|---|---|---|---|
| deepseek-v4-flash-0731 | HTTP 200 + `choices: []` | 18/20 | 空响应体，无 error 字段，延迟 40-90s |
| deepseek-v4-flash-0731 | 挂起超时（>180s） | 2/20 | 读响应体阶段挂死 |
| glm-5.2 | 200 + 明确声明无法看图 | 15/20 | 「无法直接查看或处理您上传的图片」类 |
| glm-5.2 | 200 + 泛泛而谈/幻觉 | 5/20 | 无视图片按纯文本作答 |
| **任务可用响应** | — | **0/40** | — |

> 对 relay 的直接含义：现有 relay 以 HTTP 状态码判断成败，`200+空 choices` 会被当作成功透传给客户端。**bridge 触发不能依赖上游报错，必须在发往上游之前按模型能力位前置判断**——验证了 v0.2 方案的插入点选择（通道选定后、outbound transform 前）。

## 4. ② VLM 描述质量（B，kimi-k3，20 场景）

- 自动判分 17/20 命中；人工复核 3 个未中场景：s09、s12 的描述实际完整准确（未中是 marker 设计问题），s08 为**真实失败——HTTP 200 但内容为空**。
- 修正后成功率 **19/20 = 95%**。转录质量亮点：聊天记录时间地点、报价单金额、表格数值、多图差异（三月 45→78）全部准确；重度模糊图诚实报告「无法辨认」并描述布局（理想的边界行为）。
- 延迟：中位 **38s**，P95 ~63s，长上下文场景 115s。

## 5. ③ 替换链路质量（C，40 次）+ 基线对比

| 结果 | 次数 | 说明 |
|---|---|---|
| ground truth 命中 | 30 + 2（人工修正 s09×2） | OCR/图表/表格/找不同/bug 定位全部可答 |
| 真实质量失败 | 1（s08） | 上游 B 空描述 → 下游自信幻觉出「Pinterest 画廊」 |
| 通道层故障 | 7 | 4× deepseek 超时、3× glm-5.2 空响应（与图片无关，A/C 两侧均出现） |

- 保守口径（通道故障计失败）：32/40 = **80%**；有效响应口径：32/33 = **97%**。
- 质量与 REF（gemini-3.5-flash 原生直答）对比：可自动判分场景中二者命中率相当；差异主要在延迟——**C 链路端到端中位 ≈57s（B 38s + C 19s）vs 原生 9s，约 6 倍**。

> 印证 v0.2 的路由策略：含图请求应**优先路由视觉通道**（零额外延迟），bridge 仅在无视觉通道可用时兜底。

## 6. 计划外发现 → 对 Step 1 的修正项

1. **【必须修正方案】VLM 空输出防护**：s08 全链路实测——VLM 返回 200+空文本时，若直接替换，下游模型会基于空描述自信幻觉。rewrite 前必须校验描述非空且 ≥ 最小长度（建议 30 字符），否则视为 VLM 失败进入 fallback/跳过通道。v0.2 的 fail-closed 校验（re-scan 无残留 image_url）不覆盖此情况，需补充。
2. **【必须修正方案】「200 空 choices」是主要失败形态**：bridge 的触发与成败判定完全不能依赖上游状态码；同时建议 relay 独立立项处理「200 空 choices」的通用检测（重试/标记失败），当前会被当成功透传（本次在 glm-5.2 纯文本响应中也出现 3 次，属通道通病，与图片无关）。
3. **默认 VLM 选型改为「部署环境实测 + fallback 链」**：GLM 视觉系经本网关全不可用（429/404）；kimi-k3 可靠但慢（中位 38s）。配置默认值不应硬编码 glm-4.6v-flash，文档应指导用户按自己通道实测。
4. **延迟预算确认**：VLM 描述阶段中位 38s 远超直觉预期（计划假设「10-15 分钟跑 60 次调用」低估约 3 倍），`request_timeout_seconds: 120` 的默认值合理，但 TTFB 叠加对流式体验的影响比预想大——「优先视觉通道、bridge 兜底」从优化项升级为核心策略。
