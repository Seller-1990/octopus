# 分组倍率展示与策略问题记录

> 状态：四项问题及“默认倍率上限为 4，但分组仍出现 6x item”的代码层根因已确认；当前实例数据因本机数据库不是现象发生时的数据源而未完成逐条对账。
>
> 记录日期：2026-08-08

## 1. 背景与目标

Octopus 会把 Site Account 的上游分组投影为 Projected Channel，并把可路由的 Channel / Upstream Model 组合加入模型分组。当前倍率相关行为同时跨越站点同步、站点渠道展示、模型分组维护、默认设置应用和实际路由候选选择。

本次工作需要解决四个已确认问题：

1. 进入站点渠道卡片后，待建 Key、投影 Key 等分组操作缺少该上游分组的倍率信息。
2. 倍率上限处理会物理删除模型分组中的 `GroupItem`，造成条目消失、配置丢失和后续重建循环。
3. 倍率策略暂停与同步健康暂停共用 `projection_suspended`，不同流程会互相覆盖状态。

另有一个已由代码确认根因的现象：配置中的默认倍率上限为 `4`，但模型分组中仍能看到倍率为 `6x` 的 item。原因是上限只在显式 Apply Defaults 时执行，并且执行时删除条目；实际路由规划没有在候选进入前统一执行准入过滤。

## 2. 统一口径

- **分组倍率**：上游 Site 分组对应的倍率，当前事实来源是 `SiteUserGroup.Multiplier`。
- **模型倍率**：特定 Channel / Upstream Model 的价格倍率。
- **策略采用倍率**：倍率上限策略最终用于判断该 Route Candidate 的倍率。它必须明确说明来源，不能让前端自行猜测。
- **倍率上限**：`default_multiplier_cap`。`0` 表示不限制；正数表示策略阈值。
- **未知倍率**：倍率字段为 `nil`，不能被隐式转换为 `1x`。
- **策略排除**：条目仍保留在配置中，但暂时不参与实际路由。

建议后续 API 明确返回：

- `model_multiplier`
- `group_multiplier`
- `effective_multiplier`
- `multiplier_source`
- `multiplier_cap`
- `policy_status`
- `policy_reason`

## 3. 问题一：站点渠道分组缺少倍率展示

### 3.1 已确认原因

倍率已经在同步流程中解析并持久化到 `SiteUserGroup.Multiplier`，但站点渠道页使用的 `SiteChannelGroup` 响应 DTO 没有透传该字段，响应组装函数也没有从 `SiteUserGroup` 复制倍率。

因此问题位于“数据库事实 → API DTO → 前端类型 → UI 展示”链路，而不是上游同步本身。

### 3.2 可能现象

- 数据库和同步日志已有倍率，但站点渠道页不显示。
- `0x`、低倍率、标准倍率和高倍率分组在界面上无法区分。
- 用户点击待建 Key 或投影 Key 时，无法判断是否值得创建或投影。
- 某个分组因倍率策略被排除或暂停时，页面看不到触发原因。
- 未知倍率与明确的 `1x` 容易被误认为同一状态。

### 3.3 推荐方案

1. 后端 `SiteChannelGroup` 增加可空的 `group_multiplier`。
2. 响应组装时从 `SiteUserGroup.Multiplier` 复制值。
3. 由 Token、模型或绑定临时补出的分组，在没有可靠来源时保持 `nil`。
4. 前端类型镜像后端可空字段，不把 `nil` 转为默认 `1`。
5. 在分组标题、待建 Key 对话框和投影 Key 对话框中展示分组倍率。
6. 正确区分 `0x`、明确倍率和“倍率未知”。
7. 若倍率超过当前上限，同时展示“实际倍率、上限、策略结果”。

### 3.4 实施效果

- 用户能在创建或投影 Key 前识别高倍率分组。
- 站点渠道页、模型分组页和后端策略使用同一个倍率事实来源。
- `0x` 不会因真假值判断而被隐藏。
- 未知倍率不会被误报为 `1x`。
- 该阶段补充响应与展示；倍率策略字段会与后端路由准入结果保持一致。

### 3.5 验收标准

- `nil` 显示为“倍率未知”或明确的未知态。
- `0` 显示为 `0x`。
- `0.1`、`1`、`6` 等值按真实数值显示。
- 待建 Key 和投影 Key 操作区域都能看到当前分组倍率。
- 后端字段、前端类型和 UI 展示的空值语义一致。

## 4. 问题二：倍率超限会物理删除 GroupItem

### 4.1 已确认原因

“应用默认设置”不是纯展示或纯排序操作。后端 `ApplyGroupDefaults` 会读取 `default_multiplier_cap`，计算各 `GroupItem` 的有效倍率，并对超过上限的条目执行数据库删除。同时，倍率超过上限的站点分组还会被标记为暂停投影。

倍率上限因此被实现成一次性的破坏性清理，而不是持续、可恢复的路由准入策略。

### 4.2 可能现象

- 点击“应用默认设置”后，一批模型条目从分组中消失。
- 刷新页面后条目仍不恢复，因为数据库记录已经删除。
- 用户设置的成员关系、优先级和权重可能丢失。
- Failover、轮询或加权分组的候选数下降，极端情况下分组为空。
- 高倍率备用渠道被删除后，低倍率渠道故障时无法自动兜底。
- 同步或自动分组可能再次创建条目，形成“删除 → 重建 → 再删除”的循环。
- 页面容易把该现象误判为同步丢模型，而真实触发点可能是“应用默认设置”。

### 4.3 首选方案：保留条目，持续执行策略排除

1. 不再因倍率超限删除 `GroupItem`。
2. 保留成员关系、优先级、权重和预设配置。
3. 在真正的 Route Candidate 选择路径中，根据当前有效倍率和当前上限持续判断。
4. 超限条目继续显示，但标记为“倍率超限，策略排除”。
5. 页面展示实际倍率、采用倍率、倍率来源、上限和排除原因。
6. 当倍率下降或上限提高后，条目自动恢复参与路由。
7. 对未知倍率定义明确策略，例如：
   - 宽松模式：允许路由，但显示“倍率未知”；
   - 严格模式：未知倍率也排除。

### 4.4 备选方案：独立的可恢复禁用状态

如果短期内无法在路由候选计算中动态过滤，可给 `GroupItem` 增加独立状态，例如：

- `active`
- `disabled_by_multiplier_cap`
- `disabled_manually`

“应用默认设置”只更新状态，不删除记录；条件恢复时自动重新启用。

### 4.5 不推荐但可作为短期保护的方案

如果暂时保留删除行为，至少需要：

- 执行前预览受影响的分组、渠道、模型、倍率和数量。
- 明确提示这是持久化删除。
- 二次确认。
- 把排序与倍率清理拆成两个按钮。
- 写入可审计日志。
- 提供恢复或撤销机制。

该方案只能降低误操作风险，不能解决不可逆设计。

### 4.6 实施效果

- 模型不会因倍率策略变化而从配置中消失。
- 调整上限后无需重新同步或手工重新添加。
- 手工排序、权重和成员关系得以保留。
- 页面可以区分“存在但被策略排除”和“已删除”。
- 策略行为可解释、可恢复、可审计。

### 4.7 验收标准

- 上限为 `4`、有效倍率为 `6` 的条目仍显示，但不进入实际路由候选。
- 上限提高到 `6` 或更高后，条目自动恢复。
- 有效倍率降到 `4` 或更低后，条目自动恢复。
- 同步和自动分组不会绕过策略参与实际路由。
- 重复应用默认设置不会删除条目或破坏优先级、权重。
- 前端显示的策略状态与后端实际路由决策一致。

## 5. 问题三：策略暂停与同步暂停共用状态

### 5.1 已确认原因

`SiteUserGroup` 当前使用以下通用字段表达投影暂停：

- `projection_suspended`
- `projection_suspend_reason`
- `projection_suspended_at`

倍率超限、无可用 Key、上游模型为空等不同原因共用这些字段。但它们属于不同的状态域：

- 无 Key、模型为空、同步失败属于同步健康状态。
- 倍率超过上限属于本地策略状态。
- 用户主动关闭属于人工控制状态。

当前成功同步流程可能清除通用暂停字段，从而错误解除倍率策略暂停；再次应用默认设置又可能重新暂停。

### 5.2 可能现象

- 同一分组在暂停与正常之间反复切换。
- 倍率仍超过上限，但同步成功后页面显示已恢复。
- 再次应用默认设置后又重新暂停。
- 后一次操作覆盖前一次暂停原因。
- 同时存在“无 Key”和“倍率超限”时只能保存一个原因。
- 页面状态、Projected Channel 启停和实际路由行为短时间不一致。
- 运维无法区分上游健康问题与本地成本策略限制。

### 5.3 推荐方案：独立阻断原因 + 统一决策

分别记录不同责任域的状态：

- `projection_disabled`：用户主动关闭投影。
- `sync_blocked` / `sync_status`：无 Key、模型为空、同步失败等。
- `policy_blocked`：倍率上限等本地策略。
- `policy_block_reason`
- `policy_blocked_at`

或者维护阻断原因集合：

- `manual_disabled`
- `missing_key`
- `empty_models`
- `sync_failed`
- `multiplier_cap_exceeded`

最终投影状态由单一决策函数计算：

```text
projection_active =
  site_enabled
  && account_enabled
  && !manual_disabled
  && !sync_blocked
  && !policy_blocked
  && has_usable_key
```

各模块只能维护自己负责的阻断原因，不能清除其他模块的状态。

### 5.4 恢复规则

- 成功同步只能清除同步类阻断。
- 倍率低于上限或上限提高后，由策略模块清除倍率阻断。
- 用户恢复投影只能清除人工禁用，不能绕过同步或策略阻断。
- 每次状态变化后都执行统一的投影重算和渠道启停流程。

### 5.5 实施效果

- 成功同步不会意外解除倍率策略限制。
- 一个分组可以同时表达多个阻断原因。
- 修改倍率或上限后可以准确自动暂停、恢复。
- 页面、投影状态和实际路由行为保持一致。
- 后续增加余额不足、站点维护或风险控制策略时，不需要继续复用同一个布尔字段。

### 5.6 验收标准

- “无 Key”和“倍率超限”可以同时存在并分别展示。
- 同步成功只清除同步阻断，不清除倍率阻断。
- 上限变化只维护策略阻断，不覆盖人工禁用。
- Projected Channel 启停与阻断原因计算结果一致。
- 日志能说明状态变化的责任模块、旧值、新值和原因。

## 6. 问题四：倍率上限必须是最高优先级准入规则

### 6.1 已确认原因

当前 `GroupItem.Weight`、`Priority` 和倍率排序都属于候选进入路由之后的分流或排序因素；`default_multiplier_cap` 却只在显式 Apply Defaults 时执行，实际 `CatalogPlanGroup` 没有在 `included` 之前过滤超限条目。因此高倍率条目即使“权重很大”，仍然可以参与路由。

倍率上限的语义不是“降低权重”，而是“是否具备路由资格”。它必须高于 priority、weight、余额、倍率排序和故障转移顺序。

### 6.2 推荐方案：准入过滤优先于所有软排序

路由规划统一按以下顺序计算：

```text
渠道启用 / 候选健康 / 协议兼容
→ 计算 effective_multiplier
→ multiplier cap 准入判断
→ 剩余候选再按协议、分层、余额、倍率、priority、weight 排序或分流
```

具体规则：

1. `effective_multiplier > cap`：保留 `GroupItem`，标记“倍率超限，策略排除”，不得进入路由候选。
2. `effective_multiplier` 未知：严格模式下排除，不能用 `+Inf` 绕过策略。
3. `cap = 0`：表示不限制，但仍保留倍率未知状态供页面展示。
4. 修改上限、分组倍率或报价后，立即重新计算候选并刷新路由缓存。
5. 条件恢复时自动重新纳入路由，不删除用户配置、priority、weight 或预设关系。

### 6.3 验收标准

- 上限为 `4`、有效倍率为 `6` 的条目仍显示，但不会进入实际路由候选。
- 上限提高到 `6` 或倍率降到 `4` 后，条目自动恢复。
- 高倍率条目的 `Weight`、`Priority`、Failover 顺序不能绕过 cap。
- 倍率未知的条目在严格模式下不会进入候选，并明确显示原因。
- 同步、自动分组、预设激活和备份导入后，下一次路由规划仍执行同一准入规则。
- 路由预览、分组列表和实际 Relay 选择使用同一策略结果。

## 7. 建议实施顺序

### 阶段一：补齐倍率可见性

- API 增加分组倍率与明确的空值语义。
- 站点渠道页、待建 Key、投影 Key 操作展示倍率。
- 初步展示有效倍率、倍率来源和上限。

预期：用户马上能够识别高倍率分组，并能看懂后续策略结果。

### 阶段二：停止物理删除

- 移除倍率超限删除 `GroupItem` 的行为。
- 引入持续、可恢复的路由准入策略，或短期使用独立禁用状态。
- 让分组页保留并标记被策略排除的条目。

预期：彻底解决模型条目莫名消失与删除—重建循环。

### 阶段三：拆分暂停状态

- 分离人工禁用、同步阻断和策略阻断。
- 建立统一的最终投影状态计算。
- 状态变化后统一刷新 Projected Channel 和路由缓存。

预期：消除状态互相覆盖和反复横跳。

### 阶段四：迁移、恢复与测试

- 定义旧状态字段向新状态模型的迁移规则。
- 恢复过去因倍率清理而删除的 `GroupItem`。
- 补齐单元、集成和前后端契约测试。
- 对真实环境进行只读诊断和修复前后对比。

## 8. 历史数据恢复策略

代码修改只能阻止以后继续删除，不能自动知道过去被删掉的条目原来有哪些。恢复方式按可靠性排序：

1. 从数据库备份或审计日志恢复原始 `GroupItem`、优先级和权重。
2. 如果没有完整备份，依据 Projected Channel 的模型集合与模型分组匹配规则重建候选条目。
3. 重建前生成预览，列出将恢复的分组、渠道和模型。
4. 对无法恢复原优先级、权重的条目使用明确默认值，并在报告中标记。
5. 重建后执行路由缓存刷新，但不得让倍率超限条目绕过新策略参与路由。

## 9. “上限 4 仍出现 6x item”实证问题

### 9.1 需要分别确认的事实

第一性原则要求先证明以下值分别是什么，而不是假设它们口径一致：

1. 当前生效的 `default_multiplier_cap` 是否确实为 `4`。
2. 页面显示的 `6x` 来自哪个 UI 字段。当前 Group Card 的可见倍率徽标显示的是 `group_multiplier`；模型 `multiplier` 目前主要用于排序/元数据。
3. 后端策略判断使用的 `effective_multiplier` 是多少、来源是什么。
4. 该 item 何时、由哪个入口创建或重建。
5. 创建前后是否执行过 `ApplyGroupDefaults`。
6. 倍率查询是否失败、返回未知值或使用旧快照。
7. 当前上限是一次性清理，还是在实际 Route Candidate 选择时持续执行。

### 9.2 代码层已证实结论

1. 修复前 `default_multiplier_cap` 只在显式 `ApplyGroupDefaults` 中读取，保存设置不会触发策略重算，实际路由也不执行准入过滤。
2. 修复前多个写入/重建入口不检查上限，且 Apply Defaults 会删除超限 `GroupItem`；因此 6x 条目既可能重新出现，也可能在路由中继续生效。
3. 修复后上限保存会重算独立 `policy_blocked` 状态；`ApplyGroupDefaults` 只排序和更新状态，不删除条目。
4. 修复后 `GroupGetEnabledMap`、`CatalogPlanGroup` 和最终 balancer 共同执行同一准入结果：超限或严格模式下未知倍率在排序、权重、优先级之前排除。
5. `GroupItem`、路由预览和站点渠道 API 都返回实际倍率、分组倍率、有效倍率、来源、上限和策略原因；前端保留未知与 `0x` 的区别。

### 9.3 现场数据边界

- 本机仓库中的 `data/data.db` 最后修改于 2026-08-05，且 `groups`、`group_items`、`site_user_groups` 均为空，因此它不是用户看到 6x item 时的有效现场数据源。
- 该数据库中也没有 `default_multiplier_cap` 记录；代码默认值是 `0`（不限制），不是 `4`。用户界面中的 `4` 应来自另一个正在使用的数据库或部署实例。
- 已补充 SQLite 回归测试，验证超限条目保留、路由阻断、上限提高后恢复，以及同步成功不清除策略阻断。

### 9.4 后续现场对账要求

最终结论必须包含：

- 可复现的操作顺序。
- 对应的代码入口与数据写入点。
- 数据库或测试夹具中的上限、分组倍率、模型倍率和 item 状态。
- 页面展示值与后端策略采用值的对照。
- 已证实根因、伴随缺陷和未证实可能性的明确区分。
- 修复后的行为与回归测试清单。

## Implementation Notes（实施说明与已知边界，2026-08-09）

> 两态倍率方案（阶段 1-7）实施完成后的技术边界汇总。README/README_zh 含管理员行为级简版，本文为全量技术版。

### 最终设计（两态）

- 判定规则：`cap 开启 && multiplier_known == true && multiplier > cap → blocked；其余一切（known=false / nil / cap 关闭）→ 放行 + 标注`。
- cap 只限分组倍率（key 倍率），不纳入模型倍率（模型按次/分项收费口径无法统一）。
- 候选倍率（model×group 乘积）退出准入判定与排序（D2' A'）；路由选路（catalog tier1）仍按候选倍率排序——卡片顺序与路由顺序可能不同（设计）。

### 已知边界（9 条）

1. **升级后 cap 可能长期失效**：迁移 `site_group_multiplier_known.go`（Version 2026081001）保守回填（multiplier==1 → false、无法自证 → false）。恢复依赖三条子路径，均需上游再次上报可确认信息：① 同步恢复（AutoSync 开启且 token/groups payload 携带**非 1** 倍率）；② pricing 刷新恢复（仅当 group_ratio 仍含该组——X1 保护不覆盖 true 行，停报后刷新不解除）；③ **真 1x 在无 pricing 平台（sub2api）永不标 known=true**（X4/X5 ==1 护栏）→ cap<1 时永不拦 + 永久「暂定 1x」显示；有定价平台 1x 标 true（跨平台不一致）。
2. **fail-open**：倍率/绑定查询失败时 cap 静默失效（仅 Warn 告警，`channel.go:681`、`group_multiplier_policy.go:60`）——DB 抖动时成本控制点打开，管理员从日志察觉。
3. **「暂定」徽标两语义 + 自愈条件**：保留站点旧值（**仅展示，实际计费以站点报价为准**）/ 站点未设（按 1x）；暂定状态保持到上游上报可确认倍率；keep-block「暂定 Nx」在 pricing 站点是瞬态（同周期被补 1x 覆盖），无 pricing 平台持久。
4. **两套 known 分叉**：计费快照用 quote known（`price_group_multiplier_known`，relay_logs），UI 展示用 groups known（`multiplier_known`，site_user_groups）——不同概念（计费可信度 vs 组倍率可信度）、不同键、不同刷新时点，无一致性校验；keep-block 场景 UI「暂定 5x」vs 日志「1x」系统性不一致。
5. **relay_logs 计费快照三值语义**：`price_group_multiplier_known` = nil（未解析到价格，Source unknown 或 EffectivePrice nil）/ true（真值）/ false（非分组倍率真值：全局价/暂定缺省）。对账口径：`price_source NOT IN ('unknown','') AND price_group_multiplier_known IS NOT NULL`（`''` 与 `'unknown'` 双编码盲区需前置排除）。
6. **备份 roundtrip**：quote known 已携带（json 暴露）；known=true 的 0x（免费组）恢复时保留（B1 修复，与运行时 preserve-zero 一致）。
7. **排序口径分离 + 行为变化**：卡片/自动排序「known=true 用真实值否则 1x」（原 Infinity 排末尾 → 1x 明显前移）；路由选路仍按候选倍率。ApplyGroupDefaults 持久化 priority 与前端自动排序一致（同口径）。
8. **英文阻断原因直出**（"multiplier exceeds cap (5 > 4)"），暂不翻译。
9. **幽灵行 + 手动价**：pricing known=true 行由 upsert 创建、下次同步全删重建清除（无绑定无路由影响）；手动设价（SiteModelPriceManualUpsert）known=true（F17 修复）。
10. **组级/条目级准入在绑定缺失时可能分叉**：EnforceMultiplierCap 读全部 site_user_groups（不要求绑定存在）；条目级 evaluate 的 blocked 要求绑定存在（hasGroup）——无绑定组 known=true 超限时组级标 blocked（UI「倍率阻断」）但路由放行（evaluate unknown）。触发面极窄（需无绑定 channel 的已启用 item），记录为已知边界。
